# TVPlayout PRO V22.2.1

Fix sobre la base v22.2 (`v22.2.0`).

## Sincronización continua del RTMP con el playout local

El playout local (mpv) y la salida RTMP (FFmpeg) son dos procesos
independientes. v22.2 los sincronizaba al cambiar de clip y al hacer
seek/pause, pero **durante la emisión de un mismo clip se desfasaban
progresivamente** porque FFmpeg re-encodea (latencia acumulada) mientras
mpv decodifica directo. Después de un par de minutos el RTMP podía
estar 10-30 segundos detrás del aire.

### Cambios

- **`OutputWorker.current_offset`**: nuevo property que devuelve el offset
  (en segundos) con el que el FFmpeg está emitiendo el clip actual.
  Antes no había forma de saberlo desde la UI.
- **Watcher de drift cada 2s** (`_rtmp_check_drift`): compara la posición
  de mpv (`self.player._time`) contra el offset del RTMP. Si la
  diferencia supera el umbral (default 2.0s), llama
  `output.seek_to(onair, mpv_time)` para realinear reiniciando FFmpeg con
  `-ss {mpv_time}`.
- **Suspensión de 3s después de seek/pause/cambio de clip/realineación**
  (`_rtmp_drift_suspend_until`): evita realineamientos espurios mientras
  FFmpeg está reconectando.
- **Offset inicial desde mpv directo** (`toggle_rtmp`): antes leía
  `self.ctrl.elapsed` que puede tener hasta 500ms de lag respecto del
  IPC de mpv. Ahora lee `self.player._time` directamente vía `getattr`,
  así el RTMP arranca exactamente en el offset actual del playout local.

### Comportamiento esperado

- Al iniciar el RTMP tarde (después de que el playout local está al
  aire), el RTMP ahora arranca en el mismo offset que el mpv local. Ya
  no sale "desde el principio del archivo".
- Cada 2s, si el RTMP se atrasó más de 2s respecto del playout, se
  reinicia con el offset correcto. Genera un microcorte de ~1-2s en el
  RTMP (FFmpeg termina y se reinicia con `-ss`), pero el aire nunca se
  desfasa más de 2s respecto del playout local.

## Pruebas

- `tests/test_v22_1_integration.py` (4 casos nuevos): `current_offset`
  property existe, watcher de drift existe y usa `output.current_offset`
  + `player._time`, suspensión en seek/pause/clip, offset inicial desde
  mpv directo.

## Compatibilidad

- Sin migración de BD.
- Sin cambios en la API pública existente.
- El umbral de drift (2s) es constante por ahora. Si querés que sea
  configurable, decime y lo expongo en Ajustes del sistema.

## Limitaciones conocidas

- El umbral de 2s implica que el RTMP puede estar hasta 2s desfasado
  del playout local en condiciones normales. Si bajamos el umbral a 1s
  hay más realineamientos (más microcortes). Si lo subimos a 3s el
  desfasaje puede ser visible.
- El realineamiento reinicia FFmpeg, lo que causa un microcorte de
  ~1-2s. No es instantáneo.
- Si tu servidor RTMP tiene un buffer grande, el desfasaje inicial
  puede ser mayor a 2s. En ese caso subí el umbral en
  `_rtmp_drift_threshold`.
